# TallyBook 开发路线图

按**每两周一个可运行增量**排布。每个 Phase 结束时 App 都能装到真机上用，而不是"三个月后一次性交付"。

> **范围说明**：本项目为**单币种**账本，不做汇率换算。
> 因此多币种相关的数据建模、汇率表、跨币种聚合全部不在路线图内。
>
> **相关文档**：[ARCHITECTURE](ARCHITECTURE.md)（为什么这么设计） ·
> [FEATURES](FEATURES.md)（完整功能盘点） · [RISKS](RISKS.md)（隐患与已修复缺陷）

## Phase 2 — 统计图表（2 周）

**目标**：让数据产生洞察。**本阶段已有地基**（`StatsRepository` + Vico 图表已可编译运行），
本阶段是把骨架补成完整产品。

### 2.1 已就位的能力

- 趋势图，支持 **周 / 月 / 年** 三种时间粒度切换
- 系列切换：**只看支出 / 只看收入 / 支出+收入一起看**
- 单系列渲染为**柱状图**（便于比较各桶大小），双系列渲染为**折线图**（便于看趋势与对比）
- 空桶零填充（缺口有歧义，宁可画一条零线）
- 分类占比排行（带比例条与笔数）

### 2.4 统计口径修订（按用户反馈）

原设计是"固定 12 桶窗口 + 用户自选周/月/年粒度"，存在两个问题：三个粒度彼此独立，
用户可以选出"年粒度×近12年"这种没人看的组合；而且"这个月花了多少"要滑到 12 个月里找。

改为**报表周期驱动粒度**：

| 周期 | 横轴粒度 | 点数 |
| --- | --- | --- |
| 本周 | 按日 | 7 |
| 本月 | 按周 | 4~6 |
| 本年 | 按月 | 12 |

- 每张图恒为 4~12 个点，永远可读
- 上/下一期翻页（不能翻到未来），副标题直接写明"按日/按周/按月"
- 环比基准就是上一期，与翻页一致

实现上新增 `ReportPeriod(rangeUnit, bucket)` 与 `TimeGranularity.DAY`，
并给分桶器补了按日推进和中文本地化的星期标签（设备语言是英文时，原本会显示 "Mon/Tue"）。

### 2.2 待补齐

1. **时间窗口选择器** ✅ 窗口以"当前粒度的单位数"表达，随粒度自动换标签
   （周 → 近4/8/12周；月 → 近3/6/12月；年 → 近3/5年）。
   切粒度时若原窗口不存在于新选项（如"12周"→"年"没有"12年"），自动回落到该粒度的默认值。
2. **分类下钻** ✅ 点分类占比行 → 该分类在当前窗口的明细
   - 区间由统计页**传入原始边界**而不是在详情页重算，所以列表与点击的那一行数字必然一致
   - 详情页合计与占比行同口径（支出减退款、忽略转账），并包含退款行（显示为 `+`）
   - "未分类"与"具体分类"用两条独立 SQL：`getPage` 里 `null` 表示"不筛选"，这里 `null` 表示
     "真的没有分类"，同一个值两种含义会埋 bug
3. **环比** ✅ 与紧邻的等长区间对比，标注"较上期支出 +12.4%"
   - 判定逻辑抽成 `PeriodComparison`（8 条单测），专门处理三个边界：
     上期为 0 → 显示"上期无记录"而不是 "+∞%"；两期都为 0 → "持平"；本期为 0 → "−100%" 是真信号
   - 上涨用 error 色、下降用 primary 色、无基线用中性色——**颜色表示好坏，不是表示方向**
   - 同比（去年同期）未做：周度粒度下"去年同期"需要跨年周对齐，价值低于复杂度
4. **日历热力图**：按天消费强度，这是"看全年"的正确形态
   （`StatsRepository.observeDailyTotals` 已就位，等 UI）
5. **图表可访问性**：TalkBack 需要能读出"11 月支出 1234 元"，
   不能只有一个视觉图形

### 2.3 技术要点

- **切粒度必须用 `flatMapLatest`**（已实现）：否则慢的旧查询会覆盖新图表
- **分桶只有一个实现**：SQL 只按天聚合，周/月/年分组由 `TrendBucketer` + `DateProvider` 完成。
  早期让 SQL 用 `strftime('%W')`、Kotlin 用 `WeekFields` 分别算桶键的方案，实测 753 天里有
  377 天不一致，导致周视图长期静默为 0 —— 详见 [RISKS §A1](RISKS.md)
- Vico 只接受 `Double`，传入前做 `/100.0` 是**显示层**边界；
  若将来支持零小数位币种（JPY），这里要改成按 `fractionDigits` 换算（代码已标注）
- 图表最多渲染 12~24 个桶；更多数据点应换形态（热力图/月度条），不要硬塞折线图
- **选择状态要进 `SavedStateHandle`**（[RISKS B6](RISKS.md)）：ViewModel 能扛旋转，
  扛不住进程回收；不处理就会出现"回来发现又变回月视图"
- 图表要有无障碍描述（"11 月支出 1234 元"），不能只有一个视觉图形

**验收**：图表数值与 SQL 直查逐项一致（对拍测试，**必须同时驱动 SQL 与 Kotlin 两端**）；
切换粒度后快速来回点击 10 次，图表不出现旧数据。

## Phase 3 — 预算（2 周）

**目标**：管住钱。**本阶段已有地基**（`BudgetRepository` 的周期评估、配速、期末推算已实现）。

### 3.1 已就位的能力

- **每周 / 每月**预算（`BudgetPeriod.WEEKLY` / `MONTHLY`）
- 周期边界用用户时区计算，周从周一开始，且与图表共用同一个 `weekStartsOn`
- 进度条 + 超支判定 + **配速提示**（"花得比时间快" / "节奏良好"）
- **期末超支推算**（按当前日花费速度外推，前 3 天不推算避免噪音）
- 支持按分类（含/不含子分类）或全部分类设预算

### 3.2 待补齐

1. **预算增删改 UI**：新建、编辑限额、停用、删除
2. **超支提醒通知**（前台触发版 ✅，后台定时 ⏳）
   - [x] 判定逻辑抽成纯函数 `BudgetAlertPolicy`（11 条单测）：80% 提醒一次、超支再提醒一次
   - [x] 去重键 `budgetId|periodKey|level` 持久化在 DataStore，**新周期自动重置**、升级档位仍会提醒
   - [x] 通知渠道在 `Application` 启动时注册；`POST_NOTIFICATIONS` 首次启动请求，拒绝则静默降级
   - [x] 触发时机：应用启动 + **记完一笔保存后**（用户最想知道超支的时刻）
   - [x] 真机验证双向：有去重记录时重启不发；清掉去重记录后重启立即发
   - [x] `WorkManager` 每日后台检查（`PeriodicWorkRequest`，`KEEP` 策略避免每次启动重置周期）
   - [x] 设置页开关 + 权限状态：被拒绝时显示"系统未授权通知"并提供跳转系统设置的按钮
   - [x] 两道独立闸门：用户开关（DataStore）+ 系统权限，任一为否都不发
   - [x] 真机验证：开关关闭 → 即使清空去重记录也不发；重新开启 → 立即恢复
3. **多预算并存**：一个月度总预算 + 若干分类预算，
   分类预算之和超过总预算时要给出提示（这是用户常见的配置错误）
4. **预算历史**：查看过去各周期的执行情况（需要按周期聚合的历史查询）

### 3.3 技术要点

- **预算计算放 Repository 层，不要写进 DAO 的复杂 CASE**：
  周期边界、子分类展开、配速判断都是业务规则，SQL 里表达会不可测
- 子分类展开用**递归 CTE 一次查完**（`CategoryDao.subtreeIds` 已实现），
  不要按子分类逐个查询
- ⚠️ **当前实现有 N+1 查询**（[RISKS B5](RISKS.md)）：每个预算 2~3 次查询。
  预算数超过 5 个时应改为一次 `GROUP BY` 批量算
- **`daysElapsed` 首日计为 1 天**（已实现并测试锁定）：返回 0 会让配速除零
- ⚠️ **改预算前先修 `@Upsert` 覆盖 `created_at`**（[RISKS B3](RISKS.md)）：
  Room 的 `@Upsert` 在冲突时全列 UPDATE，会把创建时间重置
- 通知任务必须**幂等**：同一天重复执行不能重复提醒
- 通知需 `POST_NOTIFICATIONS` 运行时授权（Android 13+），没授权就**静默不生效**，
  必须在设置页展示授权状态（[RISKS D1](RISKS.md)）

**验收**：设一个月度餐饮预算，超支后收到通知且不重复；
关闭通知后不再打扰；跨月后自动重置提醒状态。

## Phase 4 — 数据主权（2 周）

**目标**：用户对数据有完全掌控权。这是记账 App 的信任基石。

1. **导出** ✅
   - [x] CSV（给表格软件）+ JSON（完整备份），走 SAF `CreateDocument`，无需存储权限
   - [x] JSON 带 `schemaVersion`，字段稳定；含账户/分类/流水/预算，**并保留 `deletedAt`**
   - [x] CSV 处理三件事：UTF-8 BOM（Excel 中文不乱码）、RFC 4180 引号、公式注入中和
   - [x] 金额写成纯小数（`1234.56`），不带符号与千分位，表格软件才会按数字解析
   - [x] 真机验证：导出到 Downloads，用 Python `csv`/`json` 解析核对结构
2. **导入** ✅（JSON 版）
   - [x] 先**预览再确认**：显示将写入多少条、多少条已存在会被跳过、多少账户/分类/预算
   - [x] **幂等**：按 id 去重，同一文件导入两次不会翻倍（真机验证：第二次显示"159 条已存在"，
         导入后月度合计像素级不变）
   - [x] **整体事务**：任何失败（枚举无法识别、外键、磁盘满）都回滚，不留半份数据
   - [x] **写入前拒绝**：引用了不存在账户的备份会被拦下，而不是写到一半外键报错
   - [x] `schemaVersion` 高于当前版本时直接拒绝并说明原因
   - [ ] CSV 导入（列映射 + 日期/金额解析 + 疑似重复检测）
3. **自动备份**：`WorkManager` 定期写 SAF 目录（用户授权），保留 N 份轮转
4. **可选云同步**（末期或单独排期）
   - 建议先做 **WebDAV**（坚果云 / Nextcloud 生态），比自建后端成本低
   - 同步模型：`updatedAt` + 墓碑记录（`deleted_at`），冲突时"保留双方"而非静默覆盖
   - **单币种让同步简单很多**：不需要传汇率表，也不需要处理跨设备汇率不一致

**技术要点**
- 导出时**不要**在主线程拼大字符串，用流式写
- ⚠️ **CSV 必须防公式注入**（[RISKS C3](RISKS.md)）：以 `=` `+` `-` `@` 开头的备注
  在 Excel/Numbers 里会被当公式执行。导出时加 `'` 前缀或前置 `\t`
- CSV 要处理引号、换行、逗号（自测要覆盖这三类脏数据）
- 导入必须**先预览再提交**，且整体在一个事务里；失败要能整体回滚
- ⚠️ **导入要校验金额范围**（[RISKS B2](RISKS.md)）：`Money` 溢出会抛未捕获的
  `ArithmeticException`，CSV 里一个超大数字就能崩溃
- ⚠️ **SAF 授权要持久化**：不调 `takePersistableUriPermission`，重启后备份静默失败，
  用户会以为一直在备份（[RISKS C5](RISKS.md)）。UI 上要显示"上次备份时间"
- 导出文件是**明文财务数据**，应提供加密备份选项（[RISKS C4](RISKS.md)）

**验收**：导出 → 清空 → 导入，账户余额、分类、明细数量完全一致；
用一条备注为 `=1+1` 的记录导出，Excel 打开后显示的是文本而不是 `2`。

## Phase 5 — 安全与体验打磨（2 周）

1. **隐私锁**：`BiometricPrompt` + 前台超时（切后台 N 分钟后重新验证）
2. **数据加密（可选）**：SQLCipher + `Android Keystore` 派生密钥。
   注意会显著增加 APK 体积与首次打开耗时，**建议做成设置项而非默认**
3. **截图与任务缩略图防护**（[RISKS C2](RISKS.md)）：隐私锁开启时加 `FLAG_SECURE`。
   代价是无法截图，需给用户开关
4. **备份排除规则校验**（[RISKS C1](RISKS.md)）：`backup_rules.xml` 按文件名排除 DB，
   改 `TallyDatabase.NAME` 而忘改 XML 就会把明文账本传到云。加一条构建期断言
5. **无障碍**：TalkBack 标签、字体缩放 200% 不截断、对比度校验
6. **适配**：平板/折叠屏、横屏
7. **性能**：Baseline Profiles、启动耗时埋点、图表首帧、10 万条列表滚动基线
8. **平台授权**：`POST_NOTIFICATIONS`（Android 13+）与精确闹钟（Android 12+）的申请时机与降级
9. **上架准备**：隐私政策、数据安全表单（**明确声明"数据仅存本地"**）

## 风险登记（摘要）

完整清单见 **[RISKS.md](RISKS.md)**（含严重度、触发条件、检测方式、修复状态）。这里只保留头部风险：

| --- | --- | --- |
| 金额累加错 | 严重，摧毁信任 | ✅ 已修复（`plus` 拿到接收者导致 `10+20=20`）；测试锁定 |
| 周分桶语义不一致 | 严重，图表静默全为 0 | ✅ 已修复（SQL 只聚到天）；实测 377/753 天曾不一致 |

| 范围蔓延 | 高，永远发不出 | 严格按 Phase 交付；[FEATURES §J](FEATURES.md) 已写明"明确不做"的清单 |
