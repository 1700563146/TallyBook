# TallyBook 功能清单

> 完整功能盘点，含**尚未进入路线图**的功能。用途有两个：
> 1. 避免"做到一半才发现漏了刚需"
> 2. 标出哪些功能其实是**数据模型决策** —— 现在加一列很便宜，上线后再加要写迁移 + 补历史数据
>
> 图例：✅ 已实现 · ◐ 部分实现 · ○ 未开始 · ◇ 需产品决策
> 优先级：P0 = MVP 必须有 · P1 = 首个正式版 · P2 = 后续迭代 · P3 = 可选

## 0. 最重要的一节：越早做越便宜的数据模型决策

下面这些**不是功能，是形状**。它们现在加上只是几行代码；等有了用户数据再加，就是
一次 schema 迁移 + 历史数据回填 + 一段时间的双写兼容。

| 决策 | 现在不加的代价 | 建议 |
| --- | --- | --- |
| **`ledgerId`（多账本）** | 生活/生意/旅行账混在一起，后期拆分要用户手工分类迁移，几乎没人愿意做 | 现在就在 `transactions` / `accounts` / `categories` / `budgets` 加列，默认单一账本 |
| **`local_date` 冗余列** | 见 RISKS B1：时区一变，历史报表数字会变。用户出国回来发现上月支出变了 = 信任崩塌 | 写入时把 `yyyy-MM-dd`（当时时区）固化一列，报表按它分桶 |
| **`refundOfId`（退款关联）** | 退款只能记成"负数支出"或"反向收入"，两者都会污染统计口径 | 加一列自引用，与 `counter_account_id` 同样的模式 |
| **`status`（报销/待确认）** | 垫付的钱算不算支出？没有状态就只能靠备注约定 | 加 `reimbursable` + `reimbursed_at`，统计默认排除未报销 |
| **同步字段** | `updatedAt` / `deletedAt` 已有 ✅，缺 `deviceId` 与 `version` | 云端同步时按 `(id, version)` 做 last-write-wins |
| **`attachment` 表** | 凭证图片不能塞进 `note` | 独立表（`transactionId` + `uri` + `mime` + `size`），文件放 app 私有目录 |

> 这一节的判断标准：**如果这个字段决定"一条记录是什么形状"，现在就加；如果只是"多一个按钮"，可以等。**

### A8 为什么退款是 P0 而不是锦上添花

用户退款是高频事件（网购退货、取消订阅）。三种常见记法都有问题：

| 记法 | 问题 |
| --- | --- |
| 记一笔"负数支出" | 与模型"金额恒为正"冲突；若强行允许负值，所有 `SUM` 语义都变含糊 |
| 记一笔"收入" | 凭空增加收入，月度收入统计虚高 |
| 编辑原记录 | 丢失历史，且退款通常只退一部分 |

正确做法：**退款是独立一条 `INCOME` 记录，带 `refundOfId` 指向原支出**，
统计口径 = 支出 − 退款，且分类占比里能看到"这个分类被退了多少"。
这需要模型先有一列，所以列在第 0 节。

### B4 对账：一个容易被忽略但必须有的功能

用户手上有 1000 元，App 说 985 元。没有对账功能，用户只能猜测并留着一个永远错的余额；
有对账，用户点"调整为实际余额"，App 生成一条**调整记录**并保留差异。

关键设计：调整记录**不计入收支统计**（否则月度账目凭空多出 15 元），
只影响账户余额。这需要一个独立的 `kind = ADJUSTMENT`，与 `TRANSFER` 同级的处理。

## J. 明确不做（写下来是为了避免反复讨论）

| 不做 | 理由 |
| --- | --- |
| 多币种换算 | 产品决策，见 ARCHITECTURE §「关于单币种」。它消除了汇率表、缺汇率状态、跨币种聚合三类 bug |
| 投资/股票盈亏跟踪 | 完全是另一个产品。记账是"过去花了多少"，投资是"资产现在值多少" |
| 记账社交 / 排行榜 | 财务数据天然私密；排序与分享会制造比较焦虑，且引入隐私风险 |
| 广告 / 卖数据 | 与"数据只存在本地"的承诺直接冲突 |
| AI 自动记账（无确认） | 记错的钱比没记更糟。可以做"建议"，但必须由用户确认 |
